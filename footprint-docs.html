⚡💧 Environmental Footprint Metrics

How pi estimates the energy and water consumed by each chat session

footer.js interactive mode v1 — baseline estimates

Where it appears

The energy (⚡) and water (💧) estimates are shown in the interactive-mode footer, on the same line as the token counters and dollar cost, in the bottom-left corner.

↑12k ↓3.4k R8k $0.042 ⚡28.5Wh 💧 0.051L claude-sonnet-4

Values are cumulative across the whole chat session and update every time the model responds.

The formulas

The calculation is a three-step chain — from raw model compute, to full facility energy, to water evaporated for cooling.

1 · IT-equipment energy (Wh) E_it = (Input_Tokens × E_in) + (Output_Tokens × E_out × thinking_multiplier)
2 · Total facility energy (Wh) — includes cooling, networking, lighting E_total = E_it × PUE
3 · Water consumed (mL) — evaporative cooling Water_mL = E_total_Wh × WUE
Why E_total × WUE comes out in mL
WUE is typically expressed as litres of water per kWh of energy. Since 1 L/kWh = 1 mL/Wh (both are 10⁻³), multiplying facility-Wh by WUE gives millilitres directly — no extra conversion needed.

The 1.5× multiplier on reasoning-model output tokens accounts for hidden "thinking" tokens that aren't reported by the API but still consume compute.

How pi picks a model class

Classification happens per-response in classifyModel(model). It uses the model's reasoning flag first, then falls back to a case-insensitive regex on the model ID: 

if (model.reasoning) → "reasoning"
else if (/mini|small|haiku|nano|flash|8b|7b|3b|1b|phi|gemma/.test(id)) → "small"
else → "frontier"

Examples → small

  • gpt-4o-mini
  • claude-3-haiku
  • gemini-flash
  • llama-3-8b
  • phi-3

Examples → frontier

  • gpt-4o
  • claude-sonnet-4
  • gemini-pro

Examples → reasoning

  • o1, o3
  • deepseek-r1
  • Any model with reasoning: true in the registry

Token accounting

  • Input_Tokens = fresh input + cache-read + cache-write
  • Output_Tokens = generated tokens as reported by the provider
  • Cache tokens are counted because they still move through the model

Worked example

A session with Claude Sonnet 4 (frontier class) using 12,000 input tokens and 3,400 output tokens:

E_it    = (12000 × 0.002) + (3400 × 0.007 × 1.0)
        = 24.0 + 23.8
        = 47.8 Wh

E_total = 47.8 × 1.15
        = 54.97 Wh   → shown as "⚡55.0Wh"

Water   = 54.97 × 1.8
        = 98.95 mL   → shown as "💧  0.099L"
Real-world tangibles
55 Wh ≈ running a 10 W LED bulb for 5.5 hours, or charging an iPhone ~4 times.
99 mL ≈ ~7 tablespoons of drinking water.

Caveats & assumptions

  • These are estimates, not measurements. Actual figures depend on hardware (H100 vs. TPU vs. Trainium), batching efficiency, model quantisation, and data-center location.
  • The per-token constants are order-of-magnitude values drawn from public papers & hyperscaler disclosures. Real providers rarely publish per-token telemetry.
  • PUE 1.15 assumes a modern hyperscale facility. Older or on-prem data centers can be 1.4–2.0, which would raise both energy and water proportionally.
  • WUE 1.8 L/kWh reflects evaporative cooling. Air-cooled or seawater-cooled facilities can be dramatically lower (near 0).
  • Cache-read/write tokens are billed as input tokens here for simplicity, even though cache-reads are cheaper to serve in practice.
  • Only assistant messages contribute — user typing has no direct footprint.

Source location

All logic lives in a single file, appended near the top of the compiled footer component: 

dist/modes/interactive/components/footer.js
  ├─ classifyModel(model)      → "small" | "frontier" | "reasoning"
  ├─ estimateFootprint(...)    → { energyWh, waterMl }
  ├─ formatWh(wh)              → "28.5Wh" / "1.24kWh"
  └─ formatMl(ml)              → always litres, e.g. "0.051L" / "12.34L" / "123.4L"

Because the change was applied to the installed dist/, it will be overwritten on the next npm update of @mariozechner/pi-coding-agent. For a durable version, upstream the change or ship it as a pi extension once footer hooks are exposed.
